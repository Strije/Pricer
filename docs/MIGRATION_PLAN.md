# План переноса Pricer (десктоп PyQt6) в веб-приложение

Статус: план по результатам изучения полного набора из 50 файлов (около 26,5 тыс. строк,
из них `main.py` 7000). Получены `requirements.txt`, `check_install.py` и `settings.json`. Не присланы файлы
данных брендов и тесты, кроме `test_bulk_order.py`.

> В репозиторий не попадают секреты: ключи, пароли и `settings.json` с реальными значениями
> хранятся только вне git (см. раздел «Секреты»).

## 1. Что представляет собой приложение

Десктопная программа для автозапчастей (v1.0.3, Python 3.13, PyQt6, Windows). Ищет артикул
сразу у многих поставщиков и сводит предложения в одну таблицу.

- **Поставщики:** Profit-League, Favorit, Armtek, Forum-Auto, Mikado, ABSTD, Rossko, Avtoto,
  Tiss/TMParts, Tradesoft, ABCP (поставщик и справочник), прайсы CSV по URL.
- **Поиск:** артикул → бренд (`BrandResolver`, алиасы) → параллельные запросы с таймаутами и
  circuit breaker → кэш на 1 час → поиск аналогов → нормализация, дедупликация, пометка лучших.
- **Цены:** правила наценки по диапазонам, округление, режим «вид для клиента», доп. дни
  доставки по складам, фильтры.
- **Закупка:** корзина, заказы, заказ из файла с автоподбором, перепроверка цен и остатков,
  отправка в корзины поставщиков, защита от дублей.
- **Данные:** `config/settings.json`, JSON-файл на каждый заказ, SQLite с парами аналогов,
  файл истории поиска, подробные логи.

## 2. Ключевые наблюдения по коду

1. **Ядро уже отделено от Qt.** `provider_adapter`, `cart_store`, `order_store`, `cross_store`,
   `offer_normalizer`, `bulk_pricing` и тест `test_bulk_order` не используют PyQt. Исключение:
   три функции расчёта цены лежат в `markup_editor.py` рядом с виджетами.
2. **`main.py` на 7000 строк.** Класс `SkitchenApp` смешивает UI и бизнес-логику (поиск,
   отбор предложений, перепроверка, отправка заказов). Это главный объём работы.
3. **Рабочие инварианты, которые нельзя потерять:**
   - `internal_offer_id` = sha256 от `поставщик, бренд, артикул, цена (4 знака), склад,
     supplier_offer_id`, первые 24 символа. Алгоритм переносим байт в байт.
   - `is_cross` определяется только сверкой с запросом (`is_requested_part`), флаги поставщиков
     не учитываются (закреплено регрессионным тестом).
   - Оформление заказа выполняется один раз без повторов (`call_order_once`). Обрыв связи даёт
     статус `unknown`, решает человек.
   - Предпочтение запрошенного количества: «ровно 2 шт.» выигрывает у «упаковки 24», даже при
     стратегии «самое быстрое».
   - Наценка: первый подходящий диапазон, `to <= 0` означает «без верхней границы», округление
     вверх (`ceil` с эпсилоном) и только внутри диапазона `rounding_from … rounding_to`.
4. **Хранилища однопользовательские:** корзина в памяти, заказы файлами, блокировки в процессе.
5. **Деньги в `float`, неизвестный срок доставки как `999999*24`.**
6. **Эвристики «без возврата» зашиты под каждого поставщика** (11 разных семантик).
7. **Запись в `cross_store` теряет порции при переполнении очереди** (допустимо, данные
   накопительные), счётчик `seen_count` растёт на порцию, а не на предложение.

## 3. Целевая архитектура

- **Бэкенд:** Python 3.13, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL.
- **Фоновые задачи:** ARQ (или Celery) + Redis: поиск, пакетная проценка, перепроверка и
  отправка заказов, обновление прайсов CSV.
- **Прогресс в реальном времени:** SSE (или WebSocket) для статусов поставщиков и результатов.
- **Фронтенд:** React + TypeScript + Vite, TanStack Table (виртуализация, группировка) и
  TanStack Query. Расчёт цены на сервере, превью через API.
- **Авторизация:** сессии или JWT, роли «админ» и «менеджер».
- **Деплой:** Docker Compose (api, worker, db, redis, nginx) на VPS с фиксированным IP
  (часть поставщиков может работать по белому списку IP, в коде есть проверка внешнего IP).
- **Секреты:** ключи поставщиков в БД в зашифрованном виде (Fernet, главный ключ в переменной
  окружения). В git только `.env.example` с заглушками.

Структура репозитория:

```
backend/
  core/            # чистое ядро без Qt и без FastAPI
    pricing.py     # наценка и округление (Decimal)
    offers.py      # offer_normalizer
    quantity.py    # order_quantity
    bulk_order.py  # отбор и ранжирование предложений
    bulk_pricing.py# чтение файлов заказа
    crosses.py     # логика пар аналогов
    providers/     # адаптеры поставщиков и provider_adapter
  app/             # FastAPI: роутеры, сервисы, модели, воркеры
  tests/           # перенесённые unit-тесты + тесты на записанных ответах поставщиков
frontend/
docs/
```

## 6. Предложения по улучшению (по прочитанному коду)

1. **Деньги в `Decimal`.** Расчёт наценки, итогов и маржи переносим на `Decimal`, на границе
   API отдаём строку или число с 2 знаками. Исключит накопление ошибок округления.
2. **Срок доставки.** Неизвестный срок отдаётся как `null` и сортируется в конец, вместо числа
   `999999*24` внутри данных.
3. **Идемпотентность и блокировки в БД.** Отправка заказа: уникальный idempotency key,
   `SELECT … FOR UPDATE` по заказу, журнал `submit_attempts` с исходом. Замена блокировок
   `threading.Lock`, которые в веб-режиме не защищают между процессами.
4. **Номер заказа из последовательности.** Сейчас номер считается просмотром файлов, что
   гонкоопасно при параллельных запросах.
5. **Свёртка аналогов в памяти.** При заказе на 250 строк поставщики дают около 400 тысяч
   предложений. Свёртку делаем за один поиск и пишем одним `ON CONFLICT`, без фонового потока.
   Подтверждения считаем по длине массива поставщиков, а `seen_count` по поиску.
6. **Единое место расчёта цены.** Сервер считает цену, фронт её только показывает (превью
   правила через API). Не дублируем логику на TypeScript.
7. **Эвристики возврата как данные.** Правила вида «поле, значение, признак» выносим в таблицу
   или конфиг, по одному набору на поставщика, с тестами на живых ответах.
8. **Тесты как защита.** `test_bulk_order` переносим сразу. Для остальных модулей ядра пишем
   «характеризующие» тесты на записанных данных до начала рефакторинга.
9. **Контракт предложения.** Описываем схему предложения (Pydantic-модель) вместо
   произвольного `dict`. Сейчас ключи (`provider`/`provider_name`, `price`/`purchase_price`,
   `logo`/`warehouse`) дублируются и подстраховываются во многих местах.
10. **Закрытие ресурсов.** В `bulk_pricing._read_xlsx` и `_read_html_table` файлы и книги
    закрываем в `try/finally`. В вебе загрузки ограничиваем по размеру и защищаем от zip-бомб.
11. **Безопасность.** Секреты не попадают в логи и ответы API, на поставщиков идут только с
    сервера, роли ограничивают отправку заказов и просмотр закупочных цен (режим клиента
    выполняется на сервере, а не скрытием колонок на фронте).

**Размер и состав.** 50 файлов, 26 564 строки. 34 модуля не зависят от Qt (поставщики, хранилища,
нормализация, кроссы, бренды, чтение файлов), 13 модулей заняты интерфейсом (`settings_page` 2296

Даже консольный `bulk_price_cli.py` создаёт `QApplication` и целое окно `SkitchenApp`, чтобы вызвать

**Поставщики.** Единый неформальный интерфейс: `get_prices(article[, brand])`,
`get_brand_candidates(article)`, `get_brands(article)`, `add_to_basket(item, quantity, comment)`,
`add_to_basket_batch(rows, comment)`, плюс `ping`/`check_connection`. Транспорт у разных
поставщиков разный: REST/JSON (Armtek, Favorit, Profit-League, Forum-Auto, ABCP, Tradesoft,
ABSTD, TMParts), SOAP через `zeep` (Rossko), SOAP/POST (Avtoto), XML (Mikado), CSV по URL.
Рекомендация: описать интерфейс как `Protocol` с типизированными моделями, а адаптеры оставить
синхронными на `requests`/`zeep` в пуле потоков воркера. Переписывать на async не нужно.

**Что не переносится как есть.**

1. **`one_c_provider.py`** использует `win32com` (COM-коннектор 1С, только Windows, пароль в
   строке подключения). На Linux-сервере не запустится. Нужно решить: нужен ли он вообще, или
   заменяем на выгрузку/HTTP-сервис 1С, или оставляем маленький Windows-агент.
2. **`config_path.py`**: пути к `%APPDATA%`, `config/`, режим portable `.exe`. Заменяются на
   переменные окружения и БД.
3. **`detailed_logger.py`, `provider_diagnostics.py`**: файловые логи и отладка. Заменяются на
   структурные логи и таблицу событий.
4. **`SearchState`, `ProviderResultCache`, `ProviderCircuitBreaker`** держат состояние в памяти
   процесса. В вебе с несколькими воркерами состояние переносим в Redis (кэш с TTL, circuit
   breaker по поставщику, текущий `search_id` по пользователю). Кэш стоит ключевать с учётом
   настроек поставщиков, а не только артикула.
5. **Armtek** по умолчанию ходит по `http://` (без TLS) и перебирает несколько хостов. Перед
   переносом проверить, что поставщик поддерживает HTTPS на всех адресах, и использовать его.
6. **`requests.Session` с `trust_env=False`** обходит системные прокси. На сервере нужно
   задать это явно через конфиг, иначе исходящие запросы пойдут не тем путём.

## 10. Интеграция с 1С

**Задача:** (а) выгружать заказы клиентов в 1С, (б) записывать в 1С заказы поставщикам для учёта.
Сейчас `one_c_provider.py` читает цену из справочника через COM-коннектор `V83.COMConnector`
(файловая база, логин и пароль в строке подключения). На Linux-сервере COM недоступен и для
записи документов не подходит, поэтому его не переносим.

**Способ связи (выбрать один, по убыванию предпочтения):**

1. **HTTP-сервис или OData-интерфейс 1С** (публикация базы через веб-сервер). Pricer вызывает
   его по HTTPS с отдельным сервисным пользователем. Подходит для клиент-серверной базы или
   файловой базы, опубликованной на Windows-машине.
2. **Файловый обмен.** Pricer кладёт JSON/XML в сетевую папку или на SFTP, 1С забирает регламентным
   заданием. Самый простой вариант, если публикацию не настроить.
3. **Windows-агент рядом с 1С** с COM-подключением, принимающий задания от сервера по HTTPS.
   Запасной вариант для файловой базы без публикации.

**Архитектура (одинакова для всех способов): таблица исходящих событий (outbox).**

- Таблица `integration_outbox`: тип события (`client_order_created`, `supplier_order_submitted`),
  внешний ключ (номер заказа `ORD-…` и поставщик), полезная нагрузка JSON, статус
  (`pending / sent / failed / confirmed`), число попыток, ответ 1С, время.
- Воркер отправляет события в 1С с повторами. Внешний ключ используется как идемпотентный
  идентификатор документа в 1С, чтобы повтор не создавал дубль.
- Событие создаётся в одной транзакции с изменением заказа. Заказ у поставщика не зависит от
  доступности 1С: если 1С недоступна, выгрузка просто ждёт в очереди.
- В интерфейсе экран «Выгрузка в 1С»: статус по заказам, повтор вручную, просмотр ответа.
- Что передаём по заказу поставщику: поставщик, склад, артикул, бренд, количество, закупочная
  цена, ответ поставщика (`supplier_response`, `external_order_id`), статус позиции
  (`submitted / unknown`). Позиции со статусом `unknown` помечаем в 1С как требующие проверки.
- Что передаём по заказу клиента: клиент, менеджер, VIN, позиции, продажная цена, маржа,
  срок готовности.

**Нужно уточнить:** конфигурация 1С (УТ, Розница, БП, самописная), файловая или серверная база,

## 11. Выводы из `settings.json` и `check_install.py`

**Безопасность (срочно).** В файле реальные ключи API, пароли поставщиков и логин и пароль FTP
в самих URL. Файл прошёл через чат и облачную сессию. Рекомендую сменить эти пароли и ключи
независимо от переноса. В новой системе:
- секреты хранятся в БД зашифрованными (Fernet), в URL прайсов логин и пароль не пишутся,
  FTP-доступ хранится отдельным полем;
- URL с токенами (например, выгрузки Ostrov) считаются секретами и скрываются в интерфейсе;
- перед коммитом в CI сканируем репозиторий на секреты.

**Структура настроек для схемы БД.**
- 11 поставщиков по API и 1 поставщик ABCP в списке `abcp_suppliers` (можно несколько).
- У каждого поставщика общие поля: `enabled`, `timeout`, лимиты результатов (`direct`, `repeat`,
  `analog`, `result_limit_sort`), `warehouse_extra_days`, `allowed_warehouses` или
  `excluded_warehouses`. Выносим в общую таблицу `provider_settings` с JSONB-полем для
  специфичных параметров (адрес доставки, способ оплаты, организация и т.п.).
- У поставщиков есть параметры оформления заказа (точка доставки, оплата, договор, контакт).
  Для них нужен экран «Профиль заказа» с загрузкой справочников у самого поставщика.
- Наценки (`markup_rules`, `default_markup`, округление) и `max_crosses`, `hide_no_return`,
  `default_comment`, `provider_cache` становятся глобальными настройками.
- `managers`: сейчас список имён. В вебе это пользователи с ролями, старые имена сопоставляем.
- `url_csv`: 54 прайса (в основном выгрузки одного агрегатора, плюс FTP Фаворита и Ostrov), у
  каждого `enabled`, имя, срок по умолчанию, статус и время обновления. Это таблица
  `price_sources` и фоновое обновление раз в 24 часа (`cache_hours`).
- `expected_ip`: пустой. Для сервера заполняем фиксированным адресом.

**Из `check_install.py` следует:** кроме `settings.json` приложению нужны файлы данных
`brand_groups.json`, `brand_provider_mappings.json`, `brands.txt` (справочник брендов и
сопоставление брендов с поставщиками). Их пока не видел. Они переходят в таблицы БД и редактор
брендов. Проверка SQLite `cross_pairs.sqlite3` и внешнего IP повторяется в проверке
готовности (`/health`) нового сервиса.
